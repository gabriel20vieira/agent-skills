# Plano 3 — Tempo real (WebSocket)

> Plano 3: WebSocket autenticado em /_ws, tópicos autorizados pela matriz de permissões, broadcast depois do commit.

> Executado inline (ver o plano 2). O plano fixa ficheiros, interfaces, comportamento e testes; o código vive nos commits.

**Goal:** Um endpoint WebSocket autenticado, na mesma porta (`/_ws`), com tópicos autorizados pela matriz de permissões, broadcast feito pelos services depois do commit, e um cliente que reconecta sozinho.

**Spec:** §7 (e §12, com o health a reportar os peers).

## Decisões

- **Stack:** `nitro.experimental.websocket = true` e `server/routes/_ws.ts` com `defineWebSocketHandler`, do h3 v1 com o crossws 0.3 aninhado. Não se importa `crossws` diretamente, porque a raiz tem a 0.4 vinda do eslint.
- **Autenticação:**
  - no `upgrade`, `getUserSession(request)` mais a validação da linha em `sessions`. Se falhar, `throw new Response(401)`;
  - no `open`, volta a resolver-se a partir do peer, e guarda-se o estado.
- **Validação partilhada:** a lógica "sessão → AuthUser" sai do `01.session` para `resolveSessionAuth(session)`, usada pelo middleware e pelo WS.
- **Hub puro e testável** (`server/utils/realtimeHub.ts`, `createRealtimeHub()`). Não depende do crossws: recebe peers `{ id, send(text), close(code, reason) }`. O singleton `realtime` fica em `server/utils/realtime.ts`.
- **Protocolo e autorização de tópicos** em `shared/utils/realtimeProtocol.ts` (puro, usado pelos dois lados).
- **Payloads mínimos** (ids). O cliente volta a pedir os dados pela REST.
- **Uma instância:** o hub fica isolado atrás da interface, para um adaptador Redis futuro.

## Interfaces

```ts
// shared/utils/realtimeProtocol.ts
type ClientMessage = { type: "subscribe" | "unsubscribe", topic: string } | { type: "ping" }
type ServerMessage =
  | { type: "ready" } | { type: "pong" }
  | { type: "subscribed" | "unsubscribed", topic: string }
  | { type: "event", topic: string, event: string, data: unknown, ts: number }
  | { type: "error", code: string, topic?: string }
parseClientMessage(raw: string): ClientMessage | null
authorizeTopic(user: AuthUser, topic: string): boolean
// user:<id> só o próprio; res:<resource>[:<id>] com can(read); system todos
userTopic(id) / resourceTopic(resource, id?)

// server/utils/realtimeHub.ts
interface RealtimePeer { id: string, send(text: string): void, close(code?: number, reason?: string): void }
createRealtimeHub({ idleMs = 60_000 }) -> {
  add(peer, { user, sid }), remove(peer), touch(peer, now?),
  handle(peer, raw)                        // subscribe/unsubscribe/ping com autorização
  publish(topic, event, data), publishToUser(userId, event, data),
  disconnectSessions(sids, reason), refreshUser(userId, user | null),
  sweep(now?), stats() -> { peers, topics }
}
// server/utils/realtime.ts
export const realtime = createRealtimeHub()   // e um intervalo de sweep

// app
useRealtime(): { status, subscribe(topic) -> off, on(event, handler) -> off }
useRealtimeEvent(event, handler)            // off automático no dispose do scope
useLiveResource(resource, refresh, { id? }) // subscreve e refaz o fetch (debounce) em <resource>.* e ready
reconnectDelay(attempt, random) -> ms       // app/utils/realtime.ts (puro)
<RealtimeIndicator />
```

## Eventos do núcleo

| Evento | Tópico | Origem |
|---|---|---|
| `session.revoked` | peer da sessão, antes de fechar | `revokeSession`, `revokeUserSessions`, logout |
| `user.updated` | `user:<id>` | updateUser, reset de password, alterações à conta, mimic |
| `settings.updated` | `system` (`{ key }`, só chaves públicas) | setSetting |
| `system.maintenance` | `system` (`{ enabled }`) | setSetting("maintenance.enabled") |
| `users.created\|updated\|deleted` | `res:users` | service de utilizadores |

## Tasks

1. **Protocolo e hub** (puros), com testes:
   - parse de mensagens válidas e inválidas;
   - autorização de tópicos por role;
   - o `publish` só chega a quem subscreveu;
   - o `publishToUser` chega a todos os peers do utilizador;
   - uma subscrição não autorizada dá `error auth.forbidden`;
   - `disconnectSessions` envia `session.revoked` e fecha;
   - o `refreshUser` com menos permissões retira os tópicos e com `null` fecha;
   - o `sweep` fecha peers inativos;
   - `stats`.
2. **Servidor:**
   - `resolveSessionAuth` extraído do middleware;
   - `server/routes/_ws.ts`;
   - `realtime` singleton com sweep;
   - hooks nos services e utilitários (sessões, utilizadores, conta, settings);
   - health com `realtime: { peers }`.
3. **Cliente:**
   - plugin `realtime.client.ts`, que liga com sessão e desliga sem ela;
   - composables;
   - tratamento dos eventos do núcleo;
   - `RealtimeIndicator`;
   - teste unitário do `reconnectDelay`.
4. **Testes de API** (`test/api/realtime.test.ts`, com o pacote `ws`). Cada ficheiro de API passa a criar a sua própria DB (`freshDatabase(name)`), para não depender da ordem. Cenários:
   - uma ligação anónima é recusada;
   - o admin recebe `ready`;
   - um membro a subscrever `res:users` recebe `error auth.forbidden`;
   - um admin atualiza o membro e o membro recebe `user.updated`;
   - o admin subscrito em `res:users` recebe `users.updated`;
   - revogar a sessão do membro faz-lhe chegar `session.revoked` e fecha o socket;
   - a manutenção chega a todos como `system.maintenance`.
5. **Documentação:** CLAUDE.md e README com o padrão "publicar depois do commit" e o proxy.

## Desvios na execução (2026-09-19)

- **Testes de API sem o `@nuxt/test-utils`:**
  - um `globalSetup` faz `nuxt build` uma única vez (`SKIP_BUILD=1` reutiliza o `.output`);
  - cada ficheiro arranca `node .output/server/index.mjs` numa porta livre, com a sua própria DB (`startApp(name)`).
  - Motivo: nesta máquina, o trace de dependências do Nitro passou a demorar cerca de 4,5 minutos (sem trace, 5 s; o `.output` só tem 1221 ficheiros), e o timeout fixo de 240 s do test-utils rebentava. Com uma build partilhada, os 26 testes correm em cerca de 7 s depois da build.
- **Onde vive o singleton:** o hub `realtime` está em `server/utils/realtime.ts`, em `globalThis`, para os hot reloads em dev não perderem os sockets. `syncUserRealtime(userId)` atualiza as roles e emite `user.updated`.
- **Ping de 25 s no cliente,** para os peers não serem varridos pelo timeout de inatividade (60 s) do hub.
- **O WebSocket de teste usa o pacote `ws`,** porque o WebSocket global do Node não aceita um header `Cookie`.
