# Plano 6 — Módulos opcionais e as suas skills

> Plano 6: módulos opcionais public-site, pwa, tenancy e assistant, cada um com a sua skill.

> Executado inline. O plano fixa a forma dos módulos, o que cada um traz e como se verifica; o código vive nos commits.

**Goal:** Quatro módulos que se aplicam a um projeto criado do template (`public-site`, `pwa`, `tenancy`, `assistant`), cada um com a sua skill, e a skill `web-assistant-tool`.

**Spec:** §15 (módulos e regras do assistente), §7 (tópicos), §6 (matriz), §12 (settings).

## Forma de um módulo

```
modules/<nome>/
  README.md          o que traz, pontos de extensão tocados, como remover
  files/             ficheiros novos, com os caminhos do projeto (app/, server/, shared/, test/)
  i18n/pt-PT.json    chaves novas (fundidas nos locales do projeto)
  i18n/en-US.json
```

- **Ficheiros novos** são copiados por `skills/web-foundation/scripts/apply-module.mjs <módulo> <projeto>`. O script recusa sobrescrever ficheiros existentes e funde as chaves i18n (sem sobrescrever chaves já presentes). Tem teste `node --test`.
- **Edições a ficheiros do núcleo** (matriz de permissões, settings, navegação, `authorizeTopic`, `nuxt.config.ts`, layout) não são automáticas: a skill do módulo lista-as com o código exato. São poucas linhas e o Claude aplica-as com o contexto do projeto, que pode já ter mudado.
- **Migrações:** o módulo traz o schema Drizzle; a skill manda correr `npm run db:generate -- --name <módulo>`. Assim a migração é gerada contra o estado real do projeto.

### Desvio consciente ao spec

- **PWA sem precache gerado num hook do Nitro.** O `sw.js` faz cache-first dos assets com hash (`/_nuxt/`), network-first nas navegações com fallback para `/offline` (guardada na instalação) e ignora `/api` e `/_ws`. É mais simples, não depende do build e não serve HTML antigo com sessão de outro utilizador.

## Desvios na execução (2026-09-19)

- **Tenancy sem tópicos `org:<id>`.** O hub autoriza as subscrições de forma síncrona, só com o `AuthUser`, e a pertença a uma organização está na DB. Em vez de mudar o núcleo, `publishToOrg` lê os membros e publica no `user:<id>` de cada um. Não há autorização extra a manter, e um membro removido deixa de receber no momento. O custo (uma query por evento) é aceitável para organizações pequenas; a skill `web-tenancy` documenta `useLiveOrgResource`.
- **Nomes das foreign keys à mão no assistente.** Os nomes gerados pelo drizzle (`assistant_proposals_conversation_id_assistant_conversations_id_fk`) passam o limite de 64 caracteres do MySQL e a migração falhava. Só se viu nos testes de API do projeto de integração. A skill `web-crud-resource` avisa agora.
- **Manifest com cores em hex.** Os `swatch` dos temas são `oklch()`, que o parser de manifests não garante. O manifest usa `#ffffff`; a cor do tema continua no ícone e no `<meta name="theme-color">`.
- **Registo do service worker.** O plugin esperava pelo evento `load`, que muitas vezes já passou quando os plugins correm. Agora regista logo se `document.readyState === "complete"`.
- **Núcleo: `RealtimeIndicator`** só aparece ao fim de 2 s em baixo. Antes piscava "a reconectar" em cada carregamento, durante a primeira ligação.
- **`defineTool.ts` em vez de `tools.ts`,** para não colidir com a pasta `tools/`. O `$fetch` interno vai sem tipos: as rotas tipadas do Nitro rebentam o TS ("Excessive stack depth"), como nas páginas.
